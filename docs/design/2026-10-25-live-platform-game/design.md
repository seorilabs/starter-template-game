## 목적과 관찰 근거

현재 배포 앱의 outgame-profile은 local이다. auth와 payments는 unsupported이며 mailbox는 local이다. 네이티브 서명과 내부 업로드의 성공은 이 기능들의 실제 플랫폼 성공을 의미하지 않는다. 다음 버전은 별 세 개 예제를 유지하면서 공통 기능의 공급자 호출과 운영 결과를 사용자가 직접 확인하는 앱으로 만든다.

| 현재 확인한 사실 | 설계에 반영할 내용 |
|---|---|
| 플랫폼 anonymous credential은 IAP와 계정 연결 및 복구에 사용할 수 없음 | 플랫폼 발급 Firebase Custom Token을 교환한 검증된 계정으로 세션 발급 |
| 정식 SDK v1.0.0에 계정 연결, 복구, 우편과 IAP 검증 메서드가 있음 | 기존 공개 계약을 재사용하고 native SDK 경계를 구현 |
| 우편 보상은 entitlement 1개만 지원 | 초기 실제 우편 보상은 전용 테스트 배지. 재화 보상을 임의로 해석하지 않음 |
| Backoffice는 starter-template-*를 EXCLUDED로 분류 | 이 저장소의 실제 테스트 앱만 명시적으로 도입하고 Platform registry와 연결 |
| 현재 Backoffice 플랫폼 액션에 우편 발송 화면이 없음 | 기존 /admin/apps/{appId}/inbox를 사용하는 발송과 결과 조회 UI 추가 |

확인한 원본: Platform main36c80ba, Backoffice main3a64fa1, game-foundation maine6092fb, 중앙 계약a43f2c4. 로컬 Platform의 미추적 merge-lizard registry, Backoffice의 SEO 문서 변경과 .agent 사용자 변경은 보존한다.

## 화면 방향과 상태

[가로형 시안 세 가지](ui-concepts.html)는 UI 구성 선택용이다. 실제 서비스에 연결한 화면이나 Godot 실행 검수로 간주하지 않는다.

| 안 | 배치와 재질 | 선택 근거 |
|---|---|---|
| A 모험 캠프 | 중앙의 작은 플레이 월드, 하단6개 큰 메뉴, 나무와 크림색 버튼 | 기존 soft-adventure 방향을 이어가며 공통 기능을 찾기 쉬움. 권장안 |
| B 탐험 지도 | 지도 중심, 오른쪽2열 메뉴와 중앙 하단 시작 버튼 | 월드와 이동을 강조하는 게임형 구성 |
| C 별빛 기지 | 우주선 중심, 오른쪽2열 기능, 민트색 시작 버튼 | 어두운 배경과 강한 명암의 게임형 구성 |

목표 비율16:9, 기준1280x720, 최소568x320 가로형과844x390, 긴 화면, 태블릿을 확인한다. 최소 화면에서도 실제 입력 영역56px 이상, 주요 메뉴 라벨16px 이상을 목표로 한다. 상태는 연결 전, 연결 중, 연결됨, 시간 초과, 오프라인, 점검, 필수 업데이트, 계정 차단을 따로 표시한다. 핵심 행동은 첫 화면에서 누를 수 있어야 한다. 팝업 닫기, 포커스, 키보드와 스크롤을 실제 입력으로 검사한다.

현재 시안은 연결 전의 동일한 상태다. UID와 잔액에 성공한 듯한 예시 값을 넣지 않는다. 실제 앱의 테스트 안내 표시와 결제환경 표시는 공급자 및 서버가 확인한 값만 사용한다.

## 사용자 흐름

1. 시작에서 설정과 SDK 준비를 확인하고, 기존 로그인은 세션 갱신으로 이어간다. 신규 계정은 사용자가 새 계정 버튼을 눌렀을 때 생성한다.
2. 계정 화면에서 새 계정 만들기, UID와 지원 코드 보기 및 복사, 이전 계정 복구, 계정 연결과 관리를 큰 버튼으로 제공한다. 게임 파일 수정, 콘솔 명령과 토큰 붙여넣기는 요구하지 않는다.
3. Google 또는 Apple로 연결한 뒤 로그아웃하거나 새 테스트 계정으로 전환하고, 이전에 선택한 계정으로 복구할 수 있다. 복구는 공급자의 새 proof와 플랫폼 nonce 및 기대 UID를 검증한다. 탈퇴는 로그아웃과 구별하며 현재 계정과 영향을 표시하고 별도 확인을 받는다. 로컬에 남지 않은 계정의 식별자는 사용자가 보관한 복구 정보 입력을 지원한다.
4. 상점은 마켓이 반환한 실제 상품과 현지 가격을 표시한다. 구매, 취소, 대기, 서버 검증, 지급, 완료를 구분한다. 새로 시작하거나 복구한 계정의 구매 소유권을 다시 읽는다.
5. 우편함은 실제 플랫폼 목록을 읽는다. Backoffice에서 현재 사용자의 지원 코드 또는 플랫폼 ID를 확인하고 개별 우편을 발송한 뒤, 앱에서 읽기와 받기, 모두 받기를 수행한다. 중복 수령은 같은 서버 결과를 돌려준다.
6. 공식 테스트 광고를 호출하고 서버가 확인한 보상을 받는다. 분석 허용 상태를 보존하고 실제 이벤트 및 접속 신호가 Backoffice에서 읽히는지 확인한다.
7. Backoffice에서 점검, 업데이트, 계정 차단, 권한과 우편을 제어한 뒤 앱에서 실제 상태 변화를 확인한다. 서버 실패를 로컬 지급이나 성공 상태로 바꾸지 않는다.
8. 계정 생성과 복구, 결제 검증과 우편 지급 등의 운영 이벤트는 기존 플랫폼 이벤트 경로를 통해 등록된 Discord 채널로 보낸다. 릴리스 완료 알림도 기존 release-ops 경로를 유지한다.

공통 수정은 game-foundation 원본에서 검수한 묶음으로 설치한다. vendor 파일을 직접 수정하지 않는다. SDK 메서드가 부족하면 platform 원본에 추가하고 정식 배포와 파일 해시를 고정한다. 서버 계약의 원본은 platform/spec/openapi.yaml, 앱 등록 원본은 registry/apps다. Backoffice 설정은 ConfigRevision 및 기존 control-plane 서비스로 처리한다. 직접 SQL이나 Firestore 수정으로 검증과 권한 및 감사를 우회하지 않는다.

로컬 자동 검수는 테스트 경계의 대역과 에뮬레이터를 사용할 수 있다. 내부 배포본은 실제 서비스 모드로 강제하고 대역을 export에서 제외한다. 공통 라이브러리 reference의 대역은 검수 전용으로 유지한다.

## 제안한 제품과 환경 결정

앱 이름과 com.seorilabs.startergame은 유지한다. 플랫폼 app_id는 starter-game을 제안한다. 새 앱 전용 Firebase 프로젝트 ID 후보는 seorilabs-starter-game, 데이터 리전은 asia-northeast3이다. 이름이 이미 사용 중이면 다른 ID를 임의 생성하지 않는다. 공용 프로젝트에 이 앱의 사용자 데이터를 섞지 않는다. 기존 프로비저너와 마켓 identity를 재사용하고 필요한 앱 전용 설정만 카탈로그에 등록한다.

새 앱 버전은 기능 추가에 맞춰 v1.1.0을 제안한다. 공통 UI 계약1.0.0은 유지한다. platform SDK의 공개 API 확장이 필요하면 SDK v1.1.0 배포까지 포함하는 안이며, 필요 없으면 현행 v1.0.0을 유지한다. 이 버전들은 승인 전 제안이다.

| 제안 상품 | 유형과 지급 | 두 마켓 상품 ID | 제안 기준 가격 |
|---|---|---|---|
| 테스트 티켓1장 | 소모품, 검증한 주문당 서버 테스트 지갑에1장 지급 | starter_test_ticket_1 | 미국USD0.99, 한국KRW1500 |
| 스타터 배지 | 비소모품, 계정 귀속 영구 배지 | starter_badge | 미국USD0.99, 한국KRW1500 |

소모품 테스트 지갑은 플랫폼 주문 원장과 같은 서버 트랜잭션에 적립하고 사용자와 app_id 및 sandbox 환경으로 격리한다. 기존 게임의 수집 경제 규칙에 새 앱을 끼워 넣지 않는다. 서버가 정한 상품 매핑을 사용하고 구매 창의 성공만으로 지갑이나 배지를 지급하지 않는다. 네이티브 마켓 consume/acknowledge/finish는 서버 검증과 지급 후 순서로 처리한다. 영구 상품 복원은 서버 소유권을 다시 확인한다. 정산, 구독과 실결제는 이번 테스트의 대상이 아니다.

Play는 magicsih@gmail.com을 라이선스 테스터로 확인 및 등록하고 테스트 결제수단만 사용한다. 내부 트랙 자체는 무료 결제를 보장하지 않는다. TestFlight는 Apple sandbox를 사용한다. 상품과 가격, Google 지급 가능 merchant 상태, Apple 유료 앱 계약은 실제 콘솔에서 각각 확인한다. 법적 계약은 소유자가 검토하고 직접 수락한다.

2026-10-25 07:34 UTC의 Seori Labs 앱 목록에는 유료 앱 계약 갱신 안내가 표시되었다. 07:41 UTC의 비즈니스 화면은 `계약 없음`을 표시했다. 이 관찰만으로 새 상품 등록이 가능하다고 판정하지 않는다. 계정 소유자가 현재 법인과 계약 상태를 확인해야 하며, 에이전트는 법적 수락을 대신하지 않는다. 새 인앱상품은 아직 생성하지 않았다.

## 데이터와 실패 처리

- UID와 PUID, 지원 코드를 구별해서 표시한다. 토큰, 영수증과 purchaseToken은 로그나 Discord, Backoffice 화면 및 Git에 남기지 않는다.
- 기존 로컬 예제 진행은 다음 로그인 UID의 로컬 캐시에 한 번 이관하고, 다른 계정으로 전환할 때 섞지 않는다. 새 앱 설치에서 기존 상용 게임 데이터를 읽거나 변경하지 않는다.
- 계정 전환 세대와 작업 ID를 사용해 늦은 응답이 새 계정의 지갑, 우편과 화면을 바꾸지 못하게 한다.
- 우편과 구매 지급은 서버의 idempotency와 트랜잭션을 사용한다. 재시도와 앱 재시작으로 중복 지급하지 않는다.
- 앱은 관리자 토큰을 갖지 않는다. 운영 변경은 Backoffice의 기존 앱 범위 권한, typed confirmation, requestId와 감사 경로를 거친다.
- 소모품 테스트 지갑을 추가하는 계약과 저장 형식은 platform Obsidian 원장의 ADR과 OpenAPI에서 먼저 고정한다. 기존 SKU, 원장과 다른 앱은 보존하고 새 app_id 범위만 사용한다.

테스트 계획은 test-plan.json을 함께 승인한다. 등급L3, dev 전체 회귀와 독립 검수3회다. 새 시각 방향 선택이 필요하고 회차 추가는3회 이후 별도 승인 대상이다. TDD는 계정 전환, 중복 지급, 소모 및 복원, 우편 상태와 운영 명령에 적용한다. 아트는 선택한 시안과 같은 상태의 Godot 렌더 비교로 대체 검증한다.

설계 초안에서는 세 시안을 각각 1280×720과 568×320으로 렌더링했다. 제품 버튼 높이 56px 이상과 브라우저 오류 없음, 계정 팝업 배치를 확인했다. 이는 설계용 HTML의 확인이며 제품 기능, 실제 서버 연결, 독립 검수 3회의 통과 근거로 사용하지 않는다. test-plan.json은 중앙 계약 a43f2c4의 JSON schema 구조 검사를 통과했다. 실행 결과와 출시 gate는 아직 미실행이다.

실제 StoreKit/Play 구매창, native 로그인과 공급자 영수증은 headless 대역으로 통과시키지 않는다. 개발 환경 검증 뒤 남은 필수 항목을 구체화하고, Android와 iPhone의 대상 앱, 시간과 데이터 영향을 제시해 별도 기기 사용 승인을 받는다. 이 계획은 기기 접근을 승인하지 않는다. native 미실행 또는 provider 차단은 해당 인수조건에서 미완료로 남긴다.

## 적용과 운영

1. 화면과 이 설계 및 상품과 환경 결정을 승인받아 고정한다.
2. 원본별로 분리한 작업 티켓과 작은 PR을 만든다. 플랫폼 계약 및 앱 등록, 공통 UI 및 기능, 앱 native 연결, Backoffice 제어를 의존 순서로 검증한다.
3. 앱 전용 Firebase와 registry, catalog를 기존 자격증명 정책과 백업 및 복원 검증을 거쳐 준비한다. Secret 전체를 덮어쓰지 않고 이 앱 항목만 병합한다.
4. 플랫폼 및 Backoffice의 기존 운영 서비스에 이 앱 전용 기능을 배포한다. 공유 서비스와 웹 UI에는 테스트 트랙이 없으므로 해당 저장소의 service/web 공개 배포 계획과 중앙 gate를 별도로 적용한다. 이는 마켓 공개 출시와 구별한다.
5. 개발 환경 전체 여정과3회 독립 검수, 실제 플랫폼 서비스 왕복과 필요한 별도 승인 항목을 수행한다.
6. 확정한 새 태그의 코드, 설정 지문과 실행 근거를 고정해 Google Play internal과 TestFlight 내부 그룹까지 배포한다. 앱인토스 추가 배포는 이번 변경에서 별도 결정이 없다.
7. 데이터 삭제 없이 서비스 flag와 feature gate로 노출을 중지할 수 있게 한다. 배포 실패와 미확인 상태는 다음 성공으로 덮지 않는다.

## 승인할 항목

- 화면 A/B/C 중 하나.
- 제안한 두 상품의 ID, 유형과 미국 및 한국 가격. 다른 지역은 마켓 환산 가격과 가용성 확인 후 등록한다.
- app_id, 새 Firebase 프로젝트 및 리전, 게임 v1.1.0과 필요한 경우 SDK v1.1.0, 실제 공통 기능 전체, 공유 서비스 변경의 운영 배포, 두 마켓 내부 배포까지의 설계.
- 신규 친구와 길드, 랭킹과 푸시의 추가 여부는 사용자에게 범위 확인 중이다. 답이 없으면 현재 플랫폼 공통 기능 전체를 제안 범위로 유지하며 추가 기능을 승인으로 간주하지 않는다.
